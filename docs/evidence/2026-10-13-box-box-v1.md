# Evidence record — box-box v1 local exercise

Format follows the template in [VALIDATION.md](../VALIDATION.md). This is a synthetic,
single-machine run; it demonstrates the ingest → WAL → Parquet → query path, restart
recovery and the compression fidelity bound. It is **not** a benchmark claim and used no
game packets.

```text
Milestone / question:   Does box-box v1 persist, recover and reconstruct within the stated deviation?
Code commit:            box-box 0.2.0, this commit (no uncommitted diff beyond this record)
Date, machine:          2026-10-13, Apple M1 (MacBook), macOS 26.6.2, rustc 1.98, release build
Input origin:           synthetic generator box-box/tools/load.py: 20 cars x 10 tags at 60 Hz,
                        sine-based signals + deterministic noise; 1200 samples per request (6 frames)
Configuration:          BOXBOX_FSYNC=true (default), BOXBOX_MAX_INTERVAL_MS=1000 (default),
                        run A: BOXBOX_DEVIATION=0 (no rules); run B: BOXBOX_TAG_RULES=box-box/tools/tag-rules.example.json:
                        SPEED 0.5, THROTTLE/BRAKE 0.01, STEER 0.005, RPM 25, LAP_DISTANCE 0.25, TYRE.* 0.5
Commands:               cargo build --release; BOXBOX_DATA_DIR=<tmp> BOXBOX_BIND=127.0.0.1:18081 ./target/release/box-box
                        python3 box-box/tools/load.py http://127.0.0.1:18081 60 20 <session>; curl /sessions/<id>; curl /query ...
```

## Run A — lossless (deviation 0), 60 s of frames pushed as fast as accepted

| Measure | Value |
|---|---|
| Offered / accepted / rejected | 720,000 / 720,000 / 0 |
| Archived (after swinging door, deviation 0) | 484,279 (collinear points dropped: linear LAP_DISTANCE, constant GEAR/DRS) |
| Persisted (WAL committed with fsync) | 484,279, equal to archived |
| Wall time, client-bound single connection | 5.03 s → ≈143,000 offered samples/s |
| Request latency, 1200 samples each | p50 5.3 ms, p95 6.3 ms, max 37.2 ms (the max coincides with a segment flush) |
| Segments after graceful shutdown | 5 Parquet files, 484,479 rows, 3.6 MB on disk (≈7.4 bytes/row) |
| DuckDB `read_parquet` over the segments | schema `tag VARCHAR, ts TIMESTAMPTZ, value DOUBLE, quality UTINYINT`; row count matches |

Receive-to-accept latency as reported by the service: max 10.3 ms, mean 3.4 ms (the client
stamped `recv_ts` immediately before serialising each request, so this is JSON + HTTP + WAL).

## Run B — per-tag deviation rules, same generator

| Measure | Value |
|---|---|
| Offered / archived | 720,000 / 12,656 (56× fewer rows) |
| Rows per tag after flush | 62–73 per tag over 60 s: the 1 s heartbeat dominates because the synthetic signal is very smooth |
| Fidelity, car 0, error measured at every lossless timestamp against linear interpolation of run B | SPEED max 0.149 (budget 0.5) · BRAKE 0.0090 (0.01) · LAP_DISTANCE 0.0000 (0.25) · GEAR 0 (0) · RPM 4.47 (25) |

All channels stayed within their budget. The ratio is not representative of real telemetry;
the bound is the property being demonstrated.

## Recovery — SIGKILL without flush

1. Ingested 10 s × 5 cars into a fresh session: 30,000 offered, 568 archived and persisted,
   0 flushed to Parquet, 50 points pending (one held per tag), WAL 28.6 kB.
2. `kill -9` the process. Only `wal.log` exists for the session.
3. Restart: log reports `replayed=568`; `/sessions/sim:crash` shows `rows_in_tail=568,
   pending=0`; `/query` returns the data. The 50 held points were lost, as documented.
4. A second ingest with timestamps older than the recovered tail was rejected as
   `out_of_order` (6,000 of 6,000), confirming that ordering survives the restart. A
   subsequent graceful shutdown flushed the 568 rows to a segment.

## Limitations observed

- Throughput was measured with one Python client over loopback; the service was not the
  bottleneck and no multi-client test was run.
- The synthetic signal is smoother than game telemetry; compression ratios will differ.
- Durability was tested with SIGKILL, not power loss; macOS `fsync` was used, not
  `F_FULLFSYNC`.
- No test against real packets yet: that is the connector gate.
